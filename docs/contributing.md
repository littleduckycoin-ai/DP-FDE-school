# 把学习记录交给同学

自动归档先发生在自己的工作区。要让后续学习者和会前汇总看到，通常还需要提交PR并合并到主分支。可直接让Agent完成：“提交我今天的课前记录，创建PR。”这已经授权发布该批记录，无需反复确认。

## 学员贡献流程

1. 确认当前学习者身份、目标案例及本人记录路径。共享前检查内容适合公开；本地`.school/`不会进入提交。
2. 获取最新主分支。在自己的分支上提交，例如`reflections/alice/2026-09-07`。工作区含其他人的修改时，用独立工作区或明确文件暂存隔离本次记录，不执行清空、重置或`git add .`。
3. 仅暂存本人的目标记录，运行`python tools/validate.py`。推送个人分支，针对`main`创建PR，使用仓库PR模板说明案例、学习者和内容类型。
4. 自动检查通过后，按仓库权限合并。普通学员记录不要求CODEOWNER审核；基础资料、canon、patterns及治理文件需要CODEOWNER审核。没有合并权限时由有权限的维护者合并。
5. Agent报告准确的分支、PR链接和状态。PR尚未合并时，应明确它还没有进入主分支汇总范围。

用户可明确授权“本次会话后续自动更新这个PR”，Agent随后沿用授权。默认本地保存不等于授权发布。已经得到授权的动作不要再要求形式化确认。

## 没有仓库写权限

公共仓库可通过本人GitHub账户fork、推送自己的分支并向原仓库提PR。Agent仅使用用户有权操作的账户与凭据；不擅自改变成员权限或发邀请。没有可用登录时，先准备好准确的文件和PR说明，再指出缺少哪一步凭据。

有GitHub工具时直接创建PR；只有Git时可推送分支后使用仓库的Compare页面创建。仅给出Compare链接时，不能声称已经创建PR。CLI发布说明应通过结构化参数或临时正文文件传递，不把学员文本拼成shell命令。

## 更正与审核

自己的旧记录也不直接改写，用`revision`追加更正；问题状态单独追加。引用同伴而不覆盖同伴记录。一个新想法可以与旧想法冲突，这正是需要保留的学习过程。

正式拆解和模式先写`status: proposed`。审核者检查原文依据、观点归属、适用边界与未解决分歧。经过实际审核合并后，再使用真实审核PR将其标为`accepted`；一个标题叫“官方拆解”的文件不会自动成为共识。

基础材料只因勘误或明确的教材维护请求改动，同时维护Markdown、JSON和索引。`data/base-manifest.json`冻结基础文件摘要，不能为了让检查通过而静默重算；确有授权维护时在同一受审PR解释改动和摘要更新原因。

治理配置详见[审核与保护](governance.md)。
